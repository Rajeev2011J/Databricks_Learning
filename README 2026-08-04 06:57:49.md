# RDM_Party Backfill Spike — Notebooks

Time-boxed investigation comparing two loading strategies (monthly vs day-by-day) across
multiple Databricks cluster configurations for the historical RDM_Party backfill
(~10.75 billion records, 215 days × ~50 million records/day).

Requirements implemented: **2 (loading strategy comparison), 3 (cluster assessment),
7 (cost analysis), 8 (documentation support).**

---

## Notebooks

| Notebook | Purpose | Req |
|---|---|---|
| `Benchmark_Runner.py` | Orchestrates strategy × cluster runs; calls `RDM_Party.py` via `dbutils.notebook.run()`; captures wall-clock, records, throughput, Spark metrics | 2, 3, 4 |
| `Verifier.py` | Validates output correctness per `Load_Date`; checks non-empty partition, record count threshold (≥80%), source coverage, schema match, date assignment, source attribution, idempotency, partition additivity, lower-bound cardinality | 5, 9 |
| `Cost_Analysis.py` | Reads benchmark results; computes linear extrapolations; identifies min-cost and min-duration combinations; produces 20/25-dataset cost range; PBT-verifies Property 8 formulas | 7, 2.7, 3.8 |
| `Monitor.py` | Maintains `PENDING → IN_PROGRESS → COMPLETED / FAILED` per `Load_Date`; recovery guidance; re-run list | 6.5 |

---

## Execution Order

```
1.  Monitor (action=init)            — seed PENDING rows for full date range
2.  Benchmark_Runner (strategy=day_by_day, cluster=dab_small,  run_number=1)
3.  Benchmark_Runner (strategy=day_by_day, cluster=dab_medium, run_number=1)
4.  Benchmark_Runner (strategy=day_by_day, cluster=dab_large,  run_number=1)
5.  Benchmark_Runner (strategy=monthly,    cluster=dab_small,  run_number=1)
6.  Benchmark_Runner (strategy=monthly,    cluster=dab_medium, run_number=1)
7.  Benchmark_Runner (strategy=monthly,    cluster=dab_large,  run_number=1)
    (Repeat steps 2–7 with run_number=2 for second pass — Req 4.2)
8.  Verifier         (leave load_dates empty to verify all COMPLETED dates)
9.  Cost_Analysis    (reads all benchmark results, produces extrapolations)
10. Monitor          (action=status, confirm 100% COMPLETED)
11. Monitor          (action=rerun_list, identify any remaining FAILED dates)
```

## Key Design Decisions

- **`RDM_Party.py` is never modified.** `Benchmark_Runner` wraps it via `dbutils.notebook.run()`.
- **Write semantics:** `save_to_saradar_storage_account` in `RadarUtils.py` uses
  `mode("overwrite")` scoped to `EDL_LOAD_DTS=YYYYMMDD/` — every daily execution is
  safe to re-run without producing duplicates.
- **`MAX_PARALLEL_EXECUTIONS = 1`** (sequential) until source read contention is assessed.
- **PBT library:** `hypothesis >= 6.x` — install via cluster init script or `%pip install hypothesis`.
- **DBU cost:** stored as `0.0000` with reason `BELOW_MEASUREMENT_THRESHOLD` in the Delta row;
  actual DBU values are retrieved from the Databricks Jobs REST API post-run and back-filled
  into the results table.

## Strategy Comparison Dimensions (Requirement 2.3)

Both strategies are evaluated against all seven dimensions:

1. **Total execution time** — from `wall_clock_minutes` × extrapolated to 215 days
2. **Throughput** — `records_per_second` from benchmark
3. **Cluster utilisation** — `peak_cpu_pct` / `peak_memory_pct` (Databricks Metrics API)
4. **Scalability** — assessed in Cost_Analysis scalability section
5. **Failure recovery granularity** — day-by-day: ~50M records; monthly: sum since last verified
6. **Operational control** — per-date status in `spike_backfill_status`
7. **Compute cost** — `estimated_cost_usd` × 215 days
